## Executive Summary

### Project Purpose
The KTDA OSH Management System is a comprehensive digital platform designed to manage Occupational Safety and Health (OSH) compliance across all KTDA factories, stations, and organizational units. The system addresses regulatory requirements while providing a unified platform for safety management, incident tracking, risk assessment, and compliance monitoring.

### Key Business Drivers
- **Regulatory Compliance**: Meet Kenyan OSH Act requirements and international safety standards
- **Risk Management**: Proactive identification and mitigation of workplace hazards
- **Operational Efficiency**: Streamline safety processes across 60+ tea factories
- **Data-Driven Decisions**: Centralized safety data for informed decision-making
- **Incident Prevention**: Systematic approach to incident investigation and prevention

### Project Scope
- **Geographic Coverage**: All KTDA stations across Kenya
- **User Base**: 1,500+ employees across factories, regions, and head office
- **Functional Areas**: 6 core OSH modules with unified team management
- **Integration**: Legacy employee database synchronization and regulatory reporting

### Expected Benefits
- 40% reduction in workplace incidents through systematic risk management
- 100% regulatory compliance across all stations
- 60% improvement in safety data accuracy and accessibility
- 50% reduction in administrative overhead for safety management
- Enhanced safety culture through improved communication and training

## Project Overview

### Background
KTDA operates 60+ tea factories across Kenya with diverse organizational structures, varying compliance levels, and fragmented safety management processes. The current system relies on manual processes, paper-based records, and inconsistent data collection, leading to compliance gaps and limited visibility into safety performance.

### Current State Challenges
- **Data Fragmentation**: Safety data scattered across multiple systems and paper records
- **Compliance Gaps**: Inconsistent implementation of OSH requirements across stations
- **Limited Visibility**: No centralized view of safety performance and trends
- **Manual Processes**: Time-intensive paper-based workflows and reporting
- **Knowledge Silos**: Limited sharing of safety lessons and best practices

### Future State Vision
A unified digital OSH management platform that provides:
- Real-time safety performance visibility across all stations
- Automated compliance monitoring and reporting
- Streamlined incident management and investigation processes
- Centralized knowledge management and lesson sharing
- Data-driven safety decision making

### Project Objectives
1. **Compliance Achievement**: 100% OSH regulatory compliance across all stations
2. **Process Standardization**: Unified safety processes and procedures
3. **Data Centralization**: Single source of truth for safety information
4. **Workflow Automation**: Reduce manual administrative tasks by 60%
5. **Performance Improvement**: Enhance safety metrics and KPI tracking

```
┌─────────────────────────────────────────────────────────────┐

├─────────────────────────────────────────────────────────────┤

├─────────────────────────────────────────────────────────────┤

│  DOSHMIS API  │  Insurance Systems  │  External Reporting  │
```

### Core System Components
1. **Organizational Structure Management** - Station, department, and employee hierarchy
2. **Unified Team Management** - Generic team management for all OSH functions
3. **OSH Policy Management** - Policy creation, review, and compliance tracking
4. **OSH Committee Management** - Committee formation and activity tracking
5. **Risk Assessment Management** - Hazard identification and mitigation planning
6. **Incident Management** - Incident reporting, investigation, and learning
7. **Document Management** - Centralized document storage and version control
8. **Reporting & Analytics** - Compliance dashboards and performance metrics

### Technology Stack

#### **Backend Framework**
- **Primary**: ASP.NET Core 8.0 LTS (Long Term Support)
- **Architecture**: Clean Architecture with MediatR pattern
- **API Design**: RESTful APIs with OpenAPI/Swagger documentation

#### **Database Strategy**
- **Legacy Database**: SQL Server 2008 R2 (existing employee data)
- **New OSHA Database**: SQL Server 2019/2022 (modern features, JSON support)
- **ORM**: Entity Framework Core 8.0 with Code-First approach
- **Migration Strategy**: Dual database approach with ETL synchronization

#### **Frontend Technology**
- **Framework**: Blazor Server-Side (C# full-stack, rapid development)
- **UI Library**: MudBlazor (Material Design components for Blazor)
- **Alternative**: React.js with TypeScript (if client-side preferred)
- **Responsive**: Bootstrap 5 integration

#### **Authentication & Authorization**
- **Authentication**: ASP.NET Core Identity with cookie authentication
- **Authorization**: Policy-based authorization with custom requirements
- **Session Management**: Distributed cache with Redis (optional)

#### **File Storage & Media**
- **Local Development**: Local file system with structured folders
- **Production**: Azure Blob Storage with CDN integration
- **Media Processing**: ImageSharp for image processing
- **Document Generation**: QuestPDF for PDF reports

#### **Integration & Communication**
- **Legacy DB Sync**: Background services with Hangfire scheduler
- **External APIs**: HttpClient with Polly for resilience
- **Email**: On premise Emails
- **Logging**: Serilog with structured logging

#### **Development & Deployment**
- **IDE**: Visual Studio 2022 or Visual Studio Code
- **Source Control**: Git with GitHub
- **CI/CD**: GitHub Actions
- **Containerization**: Docker containers for deployment
- **Hosting**: on-premises IIS

#### **Supporting Libraries**
- **Validation**: FluentValidation for business rule validation
- **Mapping**: AutoMapper for object mapping
- **Caching**: Memory caching with IMemoryCache
- **Background Jobs**: Hangfire for scheduled tasks
- **Configuration**: ASP.NET Core Configuration with appsettings.json

#### **Why This Technology Stack?**

**1. Minimal Complexity:**
- **Single Language**: C# throughout (backend, frontend with Blazor, database queries)
- **Microsoft Ecosystem**: Seamless integration between ASP.NET Core, SQL Server, and Azure
- **Unified Development**: Same IDE, debugging, and deployment tools

**2. Fastest Development Time:**
- **Blazor Server**: No separate frontend build process, instant reload, server-side debugging
- **Entity Framework Core**: Code-first approach with automatic migrations
- **MudBlazor**: Pre-built components reduce custom CSS/JavaScript needs
- **ASP.NET Core Identity**: Built-in authentication with minimal setup

**3. SQL Server 2008 Compatibility:**
- **Dual Database Strategy**: Keep legacy DB unchanged, sync data as needed
- **Entity Framework Core**: Supports SQL Server 2008 with compatibility level settings
- **Background Sync**: Hangfire handles scheduled data synchronization

**4. Team Efficiency:**
- **C# Developers**: Leverage existing .NET skills
- **IntelliSense**: Strong typing throughout stack
- **Debugging**: Full-stack debugging in Visual Studio

#### **Database Architecture Strategy**

```
┌─────────────────────┐         ┌─────────────────────┐
│   Legacy SQL 2008   │ Sync    │   New OSHA Database │
│   Employee_bkp      │<------->│   SQL Server 2019+  │
│   Station           │  ETL    │                     │
│   Department        │         │   All OSHA Tables   │
└─────────────────────┘         │   Modern Features   │
                                │   JSON Support      │
                                │   Better Indexing   │
                                └─────────────────────┘
```

**Benefits of Dual Database Approach:**
- **No Legacy Disruption**: Existing systems continue unchanged
- **Modern Features**: JSON columns, advanced indexing, better performance
- **Gradual Migration**: Can migrate legacy data over time
- **Backup Strategy**: Legacy remains as backup during transition

## Data Requirements

### Data Model Overview
The system implements a normalized relational database design with the following core entities:

#### Organizational Data
- **Stations**: Hierarchical organizational units (60+ tea factories)
- **Departments**: Functional units within stations (300+ departments)
- **Employees**: Personnel master data (15,000+ employees)
- **Sections**: Operational areas within stations (Field Service, Processing, etc.)

#### Team Management Data
- **Teams**: Generic team entities for all OSH functions
- **Team Members**: Member assignments with roles and qualifications
- **Team Configurations**: Team-specific settings and requirements

#### OSH Compliance Data
- **OSH Policies**: Policy documents and compliance status per station
- **OSH Committees**: Committee configurations and activities
- **Risk Assessments**: Hazard identification and mitigation plans
- **Incidents**: Incident reports, investigations, and actions

#### Supporting Data
- **Documents**: Centralized file storage with metadata
- **Audit Logs**: Change tracking and user activity logs
- **System Configuration**: Application settings and parameters

### Data Volume Estimates
- **Stations**: 60 records
- **Departments**: 300 records
- **Employees**: 15,000 records
- **Teams**: 180 records (3 per station average)
- **Team Members**: 900 records (5 per team average)
- **Incidents**: 500 new records annually
- **Documents**: 5,000 files (average 2MB each)

### Data Quality Requirements
- **Accuracy**: 99.5% data accuracy across all modules
- **Completeness**: 95% completion rate for required fields
- **Consistency**: Data validation rules enforced at entry and processing
- **Timeliness**: Real-time updates for critical safety data

### Data Retention Requirements
- **Incident Data**: 7 years retention for regulatory compliance
- **Employee Data**: Active + 2 years post-employment
- **Audit Logs**: 5 years for security and compliance
- **Documents**: Based on document type and regulatory requirements

## Risk Assessment

### Technical Risks

#### High-Risk Items
- **RISK-T1**: Legacy database integration complexity and data quality issues
  - *Mitigation*: Extensive data analysis, cleansing tools, and staged migration approach
  - *Contingency*: Manual data entry processes and parallel system operation

- **RISK-T2**: Performance scalability with large user base and data volume
  - *Mitigation*: Load testing, performance optimization, and cloud auto-scaling
  - *Contingency*: Infrastructure scaling and architecture optimization

- **RISK-T3**: External system integration failures (DOSHMIS, Insurance)
  - *Mitigation*: API testing, fallback mechanisms, and manual reporting procedures
  - *Contingency*: Alternative reporting methods and delayed integration

#### Medium-Risk Items
- **RISK-T4**: Security vulnerabilities and data breach risks
  - *Mitigation*: Security testing, regular audits, and penetration testing
  - *Contingency*: Incident response plan and security monitoring

### Business Risks

#### High-Risk Items
- **RISK-B1**: User resistance to change and low adoption rates
  - *Mitigation*: Comprehensive change management and training programs
  - *Contingency*: Extended training periods and phased adoption approach

- **RISK-B2**: Regulatory requirement changes during development
  - *Mitigation*: Regular stakeholder engagement and flexible architecture
  - *Contingency*: Rapid development cycles and modular system design

#### Medium-Risk Items

  - *Mitigation*: Early team formation and knowledge transfer processes
  - *Contingency*: External contractor support and extended timelines
