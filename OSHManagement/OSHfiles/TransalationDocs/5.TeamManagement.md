# Team Management System Design

## Overview
The Team Management module provides a unified system for creating and managing all types of teams within stations, including OSH Committees, Risk Assessment Teams, Incident Investigation Teams, and future team requirements.

## Design Philosophy
Instead of having separate tables for each team type, this unified approach:
- Eliminates redundancy across team management
- Provides consistent team composition rules
- Enables easy extension for new team types
- Centralizes member assignment logic
- Maintains flexibility for team-specific requirements

## Database Table Design

### **1. Teams Table**
**Purpose**: Generic team management for all station-based teams
**Structure**:
- `team_id` (Primary Key - Auto-increment)
- `station_id` (Foreign Key to stations - Teams belong to specific stations)

**Team Classification**:
- `team_type` (Enum(TeamTypes) - OSH_Committee/Risk_Assessment/Incident_Investigation/Audit/Training/Other) 
- `team_name` (Text - Descriptive name for the team)
- `team_description` (Text - Purpose, scope, and responsibilities)

**Team Configuration**:
- `required_member_count` (Integer - Minimum required members)
- `max_member_count` (Integer - Maximum allowed members)
- `requires_section_representation` (Boolean - Whether all sections must be represented)

**Team Status**:
- `team_status` (Enum(TeamStatus) - Active/Inactive/Suspended)
- `formation_date` (Date - When team was formed)
- `last_review_date` (Date - When team composition was last reviewed)

**Audit Fields**:
- `is_active` (Boolean - Team active status)
- `created_at` (DateTime - Record creation timestamp)
- `updated_at` (DateTime - Last update timestamp)
- `created_by_payroll` (Employee payroll - Who created the team)

**Constraints**:
- Foreign Key: `station_id` references `stations(station_id)`
- Unique: Combination of `station_id` + `team_type` (one team of each type per station)

### **2. Team Members Table**
**Purpose**: Generic membership management for all team types
**Structure**:
- `member_id` (Primary Key - Auto-increment)
- `team_id` (Foreign Key to teams)
- `employee_payroll` (Foreign Key to employees - Team member)

**Member Role Information**:
- `member_role` (Enum(MemberRole) - Management/Employee/Outsourced/Contractor/Other/Chairman/Secretary/Coordinator)
- `member_designation` (Text - Specific role within the team)
- `section_id` (Foreign Key to sections - Which section they represent, if applicable)

**Member Qualifications**:
- `education_level` (Enum(EducationLevel) - Primary/Secondary/Tertiary/Professional/Other)
- `relevant_experience` (Text - Experience relevant to team function)
- `special_qualifications` (Text - Certifications, training, skills)

**Membership Timeline**:
- `appointment_date` (Date - When member joined the team)
- `departure_date` (Date - When member left the team)
- `departure_reason` (Text - Reason for leaving team)

**Member Status**:
- `member_status` (Enum(MemberStatus) - Active/Inactive/Suspended)
- `is_voting_member` (Boolean - Whether member has voting rights)

**Audit Fields**:
- `is_active` (Boolean - Member active status)
- `created_at` (DateTime - Record creation timestamp)
- `updated_at` (DateTime - Last update timestamp)

**Constraints**:
- Foreign Key: `team_id` references `teams(team_id)`
- Foreign Key: `employee_payroll` references `employees(payroll_no)`
- Foreign Key: `section_id` references `sections(section_id)`
- Unique: Combination of `team_id` + `employee_payroll` + `appointment_date` (prevent duplicate active memberships)

## Team Type Configurations

### **OSH Committee Teams**
- `team_type`: "OSH_Committee"
- `required_member_count`: 5 (minimum)
- `requires_section_representation`: true
- **Required Roles**: Management, Factory Employees, Section Representatives

### **Risk Assessment Teams**
- `team_type`: "Risk_Assessment"
- `required_member_count`: 5 (exactly)
- `requires_section_representation`: false
- **Required Roles**: Management(1), Employee(2), Outsourced(1), Other(1)

### **Incident Investigation Teams**
- `team_type`: "Incident_Investigation"
- `required_member_count`: 3 (minimum)
- `requires_section_representation`: false
- **Required Roles**: Management, Employee, Subject Matter Expert

## Implementation Approach

### **Phase 1: Core Team Management**
**Team Creation Interface**:
- Station selection
- Team type selection from predefined list
- Team name and description
- Required member count configuration
- Section representation requirements

**Member Management Interface**:
- Add/Remove member functionality
- Employee lookup and selection
- Role assignment dropdown
- Section assignment (if required)
- Qualification tracking

### **Phase 2: Team Type Validations**
**Business Rule Enforcement**:
- Validate required member counts
- Ensure section representation requirements met
- Check role distribution requirements
- Prevent duplicate team types per station

### **Phase 3: Integration with Modules**
**Module-Specific Extensions**:
- OSH Committee: Training status, meeting schedules
- Risk Assessment: Assessment frequency, evaluation schedules
- Incident Investigation: Case assignments, investigation status

## Data Flow

### **Team Creation Process**
1. User selects station and team type
2. System validates team type availability for station
3. User enters team details and configuration
4. System creates team record
5. User adds members according to requirements
6. System validates team composition rules

### **Member Assignment Process**
1. User selects team to modify
2. User searches for employee to add
3. System validates employee eligibility
4. User assigns role and section (if required)
5. System checks team composition requirements
6. Member added with audit trail

### **Team Validation Process**
1. System checks required member count
2. System validates section representation
3. System ensures role distribution requirements
4. System highlights missing requirements
5. Team status updated based on compliance

## Business Rules

### **Team Formation Rules**
- Each station can have one team of each type
- Teams must meet minimum member requirements
- Required roles must be filled
- Section representation enforced where required

### **Member Assignment Rules**
- Employees can be members of multiple teams
- Active employees only can be assigned
- Role assignments must be valid for team type
- Section representatives must be from assigned section

### **Team Status Rules**
- Teams marked inactive if below minimum members
- Teams suspended if key roles unfilled
- Regular review required for team composition

## Integration Points

### **Station Integration**
- Teams linked to specific stations
- Station permissions control team access
- Team status affects station compliance

### **Employee Integration**
- Employee lookup for member assignment
- Qualification tracking from employee records
- Role validation against employee data

### **Section Integration**
- Section representation requirements
- Section-based member assignment
- Coverage tracking across sections

## Success Metrics

### **Team Effectiveness**

- Team composition compliance rates
- Member retention and turnover rates

### **Coverage Analysis**
- Section representation coverage
- Role distribution across teams
- Qualification levels of team members
