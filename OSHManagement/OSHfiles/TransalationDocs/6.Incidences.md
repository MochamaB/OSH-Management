# Incident & Near Miss Management System Design

## Overview
The Incident & Near Miss module leverages the unified Team Management system to handle incident investigation teams, incident reporting, near miss tracking, systemic cause analysis, and corrective action management for each station with comprehensive audit trails and regulatory compliance.

## Requirements Analysis

### **Simple Form Fields**
1. **Incident Type** - Radio button (Near Miss/Incident)
2. **Reporting Status** - Checkboxes (Recorded on site/DOSHMIS/Majani Insurance)
3. **Gender** - Dropdown (Male/Female)
4. **Time of Incident** - Time picker
5. **Date of Incident** - Date picker

### **Document Uploads** (handled by Media table)
- Incident investigation reports
- Accident reports
- Medical certificates
- Insurance claim documents
- Investigation evidence photos

### **Complex Data Structures**
- **Investigation Team** - Managed via unified Teams system (team_type = "Incident_Investigation")
- **Incident Details** - Person injured, department, date/time, circumstances
- **Systemic Cause Analysis** - Root cause investigation with immediate/job factors
- **Control Actions** - Corrective and preventive measures
- **Lessons Learned** - Knowledge management and sharing
- **Regulatory Reporting** - Multi-platform reporting status tracking

## Database Table Design

### **1. Incident Investigation Config Table**
**Purpose**: Investigation team-specific configuration and capabilities
**Structure**:
- `config_id` (Primary Key - Auto-increment)
- `team_id` (Foreign Key to teams - where team_type = "Incident_Investigation")

**Investigation Capabilities**:
- `investigation_scope` (Text - Types of incidents team can investigate)
- `team_expertise` (Text - Team members' investigation qualifications)

**Response Configuration**:
- `response_time_hours` (Integer - Target response time for incidents)
- `escalation_threshold` (Text - When to escalate to external investigators)

**Audit Fields**:
- `created_at` (DateTime - Record creation timestamp)
- `updated_at` (DateTime - Last update timestamp)

**Constraints**:
- Foreign Key: `team_id` references `teams(team_id)`
- Unique: One config per investigation team (`team_id` unique constraint)

### **2. Incidents Table**
**Purpose**: Core incident and near miss data with comprehensive tracking
**Structure**:
- `incident_id` (Primary Key - Auto-increment)
- `station_id` (Foreign Key to stations)
- `investigation_team_id` (Foreign Key to teams - Investigation team assigned)

**Incident Classification**:
- `incident_type` (Text - Near Miss/Incident)
- `incident_severity` (Text - Minor/Moderate/Major/Fatal)
- `incident_category` (Text - Workplace Injury/Equipment Damage/Environmental/Security/Other)

**Incident Basic Information**:
- `incident_date` (Date - When incident occurred)
- `incident_time` (Time - Time of incident)
- `location_description` (Text - Where incident occurred)
- `section_id` (Foreign Key to sections - Section where incident occurred)

**Person Affected Information**:
- `person_affected_payroll` (Foreign Key to employees - If employee involved)
- `person_affected_name` (Text - If non-employee affected)
- `person_affected_gender` (Text - Male/Female)
- `person_affected_department_id` (Foreign Key to departments)
- `person_affected_type` (Text - Employee/Contractor/Visitor/Other)

**Incident Description**:
- `incident_description` (Text - Detailed description of what happened)
- `injury_description` (Text - Description of injuries sustained)
- `property_damage_description` (Text - Description of property damage)

**Reporting Status**:
- `recorded_on_site` (Boolean - Whether recorded in site register)
- `reported_to_doshmis` (Boolean - Whether reported to DOSHMIS)
- `reported_to_majani_insurance` (Boolean - Whether reported to insurance)
- `other_reporting` (Text - Other external reporting done)

**Incident Status**:
- `incident_status` (Text - Reported/Under Investigation/Investigation Complete/Closed)
- `reported_by_payroll` (Foreign Key to employees - Who reported the incident)
- `reported_date` (Date - When incident was reported)

**Audit Fields**:
- `created_at` (DateTime - Record creation timestamp)
- `updated_at` (DateTime - Last update timestamp)
- `created_by_payroll` (Employee payroll - Who created the record)

**Constraints**:
- Foreign Key: `station_id` references `stations(station_id)`
- Foreign Key: `investigation_team_id` references `teams(team_id)`
- Foreign Key: `section_id` references `sections(section_id)`
- Foreign Key: `person_affected_payroll` references `employees(payroll_no)`
- Foreign Key: `person_affected_department_id` references `departments(department_id)`
- Foreign Key: `reported_by_payroll` references `employees(payroll_no)`

### **3. Incident Investigations Table**
**Purpose**: Track investigation process and findings
**Structure**:
- `investigation_id` (Primary Key - Auto-increment)
- `incident_id` (Foreign Key to incidents)
- `investigation_team_id` (Foreign Key to teams)

**Investigation Timeline**:
- `investigation_start_date` (Date - When investigation began)
- `investigation_completion_date` (Date - When investigation was completed)
- `target_completion_date` (Date - Expected completion date)

**Investigation Process**:
- `investigation_method` (Text - Investigation methodology used)
- `evidence_collected` (Text - Description of evidence gathered)
- `witnesses_interviewed` (Text - List of witnesses and their statements)

**Investigation Findings**:
- `immediate_causes` (Text - Direct causes identified)
- `root_causes` (Text - Underlying systemic causes)
- `contributing_factors` (Text - Additional factors that contributed)

**Investigation Status**:
- `investigation_status` (Text - In Progress/Complete/Pending Review/Approved)
- `investigation_quality_rating` (Integer - Internal quality assessment 1-5)

**Audit Fields**:
- `created_at` (DateTime - Record creation timestamp)
- `updated_at` (DateTime - Last update timestamp)
- `investigation_lead_payroll` (Employee payroll - Lead investigator)

**Constraints**:
- Foreign Key: `incident_id` references `incidents(incident_id)`
- Foreign Key: `investigation_team_id` references `teams(team_id)`
- Foreign Key: `investigation_lead_payroll` references `employees(payroll_no)`

### **4. Incident Causes Table**
**Purpose**: Structured cause analysis following OSHA requirements
**Structure**:
- `cause_id` (Primary Key - Auto-increment)
- `incident_id` (Foreign Key to incidents)

**Immediate Causes (Unsafe Acts)**:
- `not_using_ppes` (Boolean - Not using Personal Protective Equipment)
- `ignoring_sops` (Boolean - Ignoring Standard Operating Procedures)
- `taking_shortcuts` (Boolean - Taking shortcuts in procedures)
- `working_without_authorization` (Boolean - Working without proper authorization)
- `other_unsafe_acts` (Text - Other unsafe acts identified)

**Job Factors (Unsafe Conditions)**:
- `poor_lighting` (Boolean - Inadequate lighting conditions)
- `slippery_floor` (Boolean - Slippery or hazardous flooring)
- `damaged_equipment` (Boolean - Equipment in poor condition)
- `unguarded_machine` (Boolean - Machine without proper guards)
- `exposed_electrical_system` (Boolean - Electrical hazards present)
- `other_unsafe_conditions` (Text - Other unsafe conditions identified)

**Additional Factors**:
- `human_factors` (Text - Personal factors that contributed)
- `organizational_factors` (Text - System/management factors)
- `environmental_factors` (Text - Environmental conditions)

**Audit Fields**:
- `created_at` (DateTime - Record creation timestamp)
- `updated_at` (DateTime - Last update timestamp)

**Constraints**:
- Foreign Key: `incident_id` references `incidents(incident_id)`

### **5. Control Actions Table**
**Purpose**: Track corrective and preventive actions from incidents
**Structure**:
- `action_id` (Primary Key - Auto-increment)
- `incident_id` (Foreign Key to incidents)

**Action Information**:
- `action_type` (Text - Immediate/Short-term/Long-term/Preventive)
- `action_description` (Text - Detailed description of action required)
- `action_category` (Text - Engineering/Administrative/PPE/Training/Other)

**Action Assignment**:
- `assigned_to_payroll` (Foreign Key to employees - Who is responsible)
- `assigned_department_id` (Foreign Key to departments - Responsible department)
- `assigned_date` (Date - When action was assigned)

**Action Timeline**:
- `target_completion_date` (Date - Expected completion date)
- `actual_completion_date` (Date - Actual completion date)
- `follow_up_date` (Date - Date for effectiveness review)

**Action Status**:
- `action_status` (Text - Pending/In Progress/Completed/Verified/Closed)
- `completion_verification_by` (Foreign Key to employees - Who verified completion)
- `effectiveness_rating` (Integer - How effective was the action 1-5)

**Action Details**:
- `implementation_notes` (Text - Details of how action was implemented)
- `resources_required` (Text - Resources needed for implementation)
- `cost_estimate` (Decimal - Estimated cost of action)

**Audit Fields**:
- `created_at` (DateTime - Record creation timestamp)
- `updated_at` (DateTime - Last update timestamp)

**Constraints**:
- Foreign Key: `incident_id` references `incidents(incident_id)`
- Foreign Key: `assigned_to_payroll` references `employees(payroll_no)`
- Foreign Key: `assigned_department_id` references `departments(department_id)`
- Foreign Key: `completion_verification_by` references `employees(payroll_no)`

### **6. Lessons Learned Table**
**Purpose**: Capture and share knowledge from incidents
**Structure**:
- `lesson_id` (Primary Key - Auto-increment)
- `incident_id` (Foreign Key to incidents)

**Lesson Information**:
- `lesson_title` (Text - Brief title of lesson learned)
- `lesson_description` (Text - Detailed lesson learned)
- `lesson_category` (Text - Technical/Procedural/Behavioral/Management)

**Applicability**:
- `applicable_to_stations` (Text - Which stations should apply this lesson)
- `applicable_to_sections` (Text - Which sections/departments)
- `lesson_priority` (Text - High/Medium/Low)

**Sharing and Implementation**:
- `shared_date` (Date - When lesson was shared across organization)
- `implementation_status` (Text - Pending/In Progress/Implemented/Verified)
- `shared_by_payroll` (Foreign Key to employees - Who shared the lesson)

**Effectiveness Tracking**:
- `follow_up_required` (Boolean - Whether follow-up monitoring needed)
- `effectiveness_notes` (Text - Notes on lesson implementation effectiveness)

**Audit Fields**:
- `created_at` (DateTime - Record creation timestamp)
- `updated_at` (DateTime - Last update timestamp)

**Constraints**:
- Foreign Key: `incident_id` references `incidents(incident_id)`
- Foreign Key: `shared_by_payroll` references `employees(payroll_no)`

## Implementation Approach

### **Phase 1: Investigation Team Setup**

**Investigation Team Creation** (via Team Management System):
- Station selection
- Create team with `team_type = "Incident_Investigation"`
- Set `required_member_count = 3` (minimum)
- Required roles: Management, Employee, Subject Matter Expert

**Investigation Configuration Form**:
- Investigation scope definition
- Team expertise documentation
- Response time configuration
- Escalation threshold settings

### **Phase 2: Incident Reporting Interface**

**Incident Entry Form**:
- Incident type selection (Near Miss/Incident)
- Date and time pickers
- Location and section selection
- Person affected information
- Incident description text area
- Reporting status checkboxes (Site/DOSHMIS/Majani)
- Investigation team assignment

**Near Miss Streamlined Form**:
- Simplified interface for near miss reporting
- Focus on potential consequences
- Quick categorization
- Immediate risk assessment

### **Phase 3: Investigation Management**

**Investigation Process Interface**:
- Investigation timeline tracking
- Evidence collection forms
- Witness interview templates
- Cause analysis structured forms
- Finding documentation
- Investigation quality checks

**Cause Analysis Form** (structured checkboxes and text):
- Immediate causes section with predefined checkboxes
- Job factors section with predefined checkboxes
- Additional factors text areas
- Root cause analysis methodology

### **Phase 4: Action & Learning Management**

**Control Actions Interface**:
- Action assignment forms
- Progress tracking dashboard
- Verification workflows
- Effectiveness assessment
- Cost tracking

**Lessons Learned Interface**:
- Lesson extraction from incidents
- Knowledge sharing workflows
- Implementation tracking
- Organization-wide communication

## Data Flow

### **Incident Reporting Process**
1. User reports incident/near miss via reporting form
2. System creates incident record with station_id
3. System assigns investigation team based on station and incident type
4. Investigation team receives notification
5. Investigation process begins with timeline tracking

### **Investigation Workflow**
1. Investigation team lead initiates investigation
2. Evidence collection and witness interviews conducted
3. Structured cause analysis completed using predefined categories
4. Root cause analysis methodology applied
5. Investigation findings documented and reviewed
6. Control actions identified and assigned

### **Action Implementation Process**
1. Control actions assigned to responsible personnel
2. Progress tracking through status updates
3. Completion verification by designated personnel
4. Effectiveness assessment after implementation
5. Follow-up monitoring for long-term effectiveness

### **Knowledge Management Process**
1. Lessons extracted from completed investigations
2. Lessons categorized and prioritized
3. Organization-wide sharing via communication channels
4. Implementation tracking across applicable stations
5. Effectiveness monitoring and feedback collection

## Business Rules

### **Investigation Team Requirements** (enforced by Team Management System)
- Minimum 3 members per team (Management, Employee, Subject Matter Expert)
- Teams must be active and properly trained
- Team assignment based on incident severity and type
- External expert involvement for complex incidents

### **Incident Reporting Requirements**
- All incidents must be reported within 24 hours
- Near misses encouraged to be reported immediately
- Regulatory reporting required for specific incident types
- Investigation must commence within defined timeframes

### **Investigation Process Rules**
- Investigation timeline based on incident severity
- Structured cause analysis mandatory for all incidents
- Root cause methodology required for significant incidents
- Investigation quality review before closure

### **Action Management Rules**
- All incidents must have control actions assigned
- Action completion verification required
- Effectiveness assessment mandatory for critical actions
- Follow-up monitoring for systemic improvements
